Bloque A2 · Preprocesamiento — ColumnTransformer y división train/test¶

Librerías que usamos en este bloque:

  • sklearn.model_selection.train_test_split — divide el dataset en entrenamiento (80%) y prueba (20%).
  • sklearn.preprocessing.OneHotEncoder — convierte variables categóricas en columnas binarias (One-Hot Encoding).
  • sklearn.preprocessing.StandardScaler — escala las variables numéricas a media 0 y desviación estándar 1.
  • sklearn.compose.ColumnTransformer — combina el encoder y el scaler en un solo objeto.

¿Por qué usar stratify=y al dividir train/test? Al dividir el dataset de forma aleatoria, podría ocurrir por azar que el conjunto de entrenamiento quede con una proporción de aprobados distinta a la del conjunto de prueba (por ejemplo, 45% aprobados en train pero solo 30% en test). Eso complica comparar resultados de forma justa y puede sesgar la evaluación.

stratify=y le indica a train_test_split que mantenga, tanto en train como en test, la MISMA proporción de cada clase (aprobado/rechazado) que hay en el dataset completo (~39.8% aprobados). Es una buena práctica estándar al dividir datos para un problema de clasificación, sobre todo cuando las clases no están perfectamente balanceadas.

¿Por qué aplicar One-Hot Encoding? La regresión logística trabaja exclusivamente con números. Una variable como historial tiene categorías (Bueno, Regular, Malo) que no tienen un orden numérico válido. Si las codificamos como 0, 1, 2, el modelo asume erróneamente que "Malo" = 2 veces "Bueno". Con OHE, cada categoría se convierte en una columna separada de 0 o 1.

El parámetro drop='first' elimina una categoría por variable para evitar la multicolinealidad perfecta (si conozco todas las columnas menos una, puedo deducirla). handle_unknown='ignore' evita que el encoder falle si en producción aparece una categoría que nunca vio durante el entrenamiento.

¿Por qué escalar las variables numéricas? La regresión logística usa un algoritmo de optimización basado en gradientes para encontrar sus parámetros. Si ingreso_usd está en miles y edad en decenas, el algoritmo puede converger más lento. StandardScaler transforma cada variable a (x − media) / desviación estándar, dejando todas las variables en la misma escala.

¿Por qué un ColumnTransformer en vez de aplicar cada técnica por separado? ColumnTransformer aplica el OneHotEncoder solo a las columnas categóricas y el StandardScaler solo a las columnas numéricas, y devuelve el resultado combinado en una sola matriz — un único objeto (preproc) en vez de codificar y escalar a mano por separado.

⚠️ Regla de oro: preproc se ajusta (fit) solo con los datos de entrenamiento. Sobre los datos de prueba (o un cliente nuevo) se aplica únicamente transform. Como verás en el Bloque A3, un Pipeline se encarga de aplicar esta regla automáticamente — nunca tendrás que llamar fit/transform a mano.

Bloque A3 · Pipeline, entrenamiento y predicción¶

Librerías que usamos en este bloque:

  • sklearn.pipeline.Pipeline — encadena el preprocesamiento (preproc) y el modelo en un solo objeto.
  • sklearn.linear_model.LogisticRegression — implementa la regresión logística.

Parámetros que usamos en LogisticRegression:

  • solver='lbfgs' — algoritmo de optimización. Es el valor por defecto y funciona bien para datasets de tamaño mediano.
  • max_iter=500 — número máximo de iteraciones. Se sube de 100 (valor por defecto) a 500 como margen de seguridad para asegurar la convergencia.
  • random_state=42 — reproducibilidad de resultados.

¿Por qué un Pipeline? Pipeline encadena preproc (Bloque A2) y el modelo en un solo objeto. Al llamar pipeline.fit(X_train, y_train), el pipeline internamente:

  1. Ajusta (fit_transform) preproc solo con X_train.
  2. Entrena el modelo con esos datos ya transformados.

Y al llamar pipeline.predict(X_test), aplica preproc.transform() (nunca fit) sobre X_test antes de predecir. La disciplina "fit solo en train" queda garantizada automáticamente — ya no hace falta llamar fit_transform/transform a mano ni preocuparse de codificar/escalar antes de entrenar.

predict vs predict_proba

El modelo no solo puede decirnos la clase predicha, sino también la probabilidad de pertenecer a cada clase:

  • predict(X) → devuelve directamente la clase (0 o 1), usando el umbral por defecto de 0.5. Si P(aprobado) ≥ 0.5 → predice 1. Si P(aprobado) < 0.5 → predice 0.

  • predict_proba(X) → devuelve una tabla con dos columnas:

    • Columna 0: P(y=0 | X) → probabilidad de ser rechazado
    • Columna 1: P(y=1 | X) → probabilidad de ser aprobado

    La suma de ambas columnas siempre es 1.0 para cada fila.

from sklearn.linear_model import LogisticRegression

    ('modelo', LogisticRegression(solver='lbfgs', max_iter=500, random_state=42)),
])

# pipeline.fit() ajusta preproc y entrena el modelo en un solo paso, usando SOLO X_train

Matriz de confusión¶

La matriz de confusión es una tabla que muestra cuántas veces el modelo acertó y en qué tipo de errores incurrió, cruzando los valores reales contra los predichos:

Predicho: 0 (Rechazado) Predicho: 1 (Aprobado)
Real: 0 (Rechazado) TN — Verdadero Negativo ✓ FP — Falso Positivo ✗
Real: 1 (Aprobado) FN — Falso Negativo ✗ TP — Verdadero Positivo ✓
  • TN (Verdadero Negativo): el modelo predijo Rechazado y el cliente era realmente malo. Correcto.
  • TP (Verdadero Positivo): el modelo predijo Aprobado y el cliente era realmente bueno. Correcto.
  • FP (Falso Positivo — Error Tipo I): predijo Aprobado pero el cliente era malo. El banco pierde dinero.
  • FN (Falso Negativo — Error Tipo II): predijo Rechazado pero el cliente era bueno. El banco pierde un cliente.

Classification Report¶

El classification_report resume en una sola tabla las principales métricas del modelo. Veamos cómo interpretar cada columna y cada fila:

Columnas:

  • precision — De todos los que el modelo predijo como clase X, ¿qué proporción realmente eran clase X?
    Precision = TP / (TP + FP)
    Alta precision → pocas falsas alarmas.

  • recall — De todos los que realmente son clase X, ¿qué proporción detectó el modelo?
    Recall = TP / (TP + FN)
    Alto recall → el modelo detecta la mayoría de los casos reales.

  • f1-score — Media armónica entre precision y recall. Útil cuando las clases están desbalanceadas.
    F1 = 2 × (Precision × Recall) / (Precision + Recall)

  • support — Número real de instancias de esa clase en el conjunto de prueba.

Filas:

  • 0 (Rechazado) — métricas para la clase negativa.
  • 1 (Aprobado) — métricas para la clase positiva (la que nos interesa detectar).
  • accuracy — proporción total de predicciones correctas sobre todas las predicciones.
  • macro avg — promedio simple de las métricas de cada clase (ignora el desbalance).
  • weighted avg — promedio ponderado por el número de instancias de cada clase (tiene en cuenta el desbalance).

Curva ROC y AUC¶

La curva ROC muestra el rendimiento del modelo a todos los umbrales posibles de clasificación.
Cada punto de la curva representa un umbral diferente y muestra:

  • TPR (Tasa de Verdaderos Positivos = Recall) en el eje Y: ¿cuántos positivos reales detecta?
  • FPR (Tasa de Falsos Positivos) en el eje X: ¿cuántos negativos clasifica mal como positivos?

El AUC (Área Bajo la Curva) resume la curva en un solo número:

  • AUC = 1.0 → modelo perfecto (no existe en la práctica)
  • AUC ≥ 0.9 → excelente · AUC 0.8–0.9 → muy bueno · AUC 0.7–0.8 → aceptable
  • AUC = 0.5 → equivale a clasificar al azar (la línea diagonal punteada)

Bloque A5 · Predicción de un caso individual¶

¿Qué hacemos aquí? El modelo está entrenado. Ahora simulamos que llega un nuevo cliente al banco y queremos saber si el modelo lo aprobaría o rechazaría — y con qué probabilidad.

Pasos para predecir un caso nuevo:

  1. Crear un DataFrame con los datos del cliente (mismas columnas que el dataset original, sin codificar).

⚠️ Por qué esto importa: aplicar pd.get_dummies directamente sobre un DataFrame de una sola fila (un único cliente) es un error real y silencioso. Con una sola fila, cada columna categórica solo tiene UNA categoría presente, así que drop_first/drop='first' la elimina por completo — el cliente terminaría codificado como si todas sus variables categóricas fueran la categoría base, sin importar su valor real, y no se lanza ningún error ni advertencia. El OneHotEncoder dentro de preproc no tiene este problema porque ya "memorizó" las categorías durante el entrenamiento — no las vuelve a derivar de la fila que recibe.

Parte C — Entrenamiento Final, Exportación y Uso del Modelo¶

Cierra el ciclo completo: de un pipeline evaluado en un notebook, a un archivo listo para usarse en cualquier otro programa.

Bloque C1 · Entrenamiento final, exportación y uso del modelo¶

¿Por qué reentrenar?

El pipeline de los Bloques A3–A4 se entrenó solo con el 80% de los datos (X_train); el 20% restante (X_test) se reservó únicamente para medir qué tan bien generaliza el modelo a datos que no vio.

Una vez aprobado ese resultado, el pipeline que se usaría en producción se reentrena con el 100% de los datos disponibles — ya no necesita guardar un conjunto de prueba propio, porque su desempeño ya se estimó en el paso anterior. Más datos de entrenamiento generalmente producen un modelo mejor.

Librería que usamos en este bloque:

  • joblib — guarda y carga objetos de Python (como un pipeline entrenado) en un archivo .pkl.

¿Por qué exportar pipeline_final completo, y no el modelo y el preprocesamiento por separado?

pipeline_final incluye tanto preproc como el modelo, en un solo objeto. Al exportarlo con joblib.dump(), un único archivo .pkl contiene todo lo necesario — no hay riesgo de guardar el modelo junto a un preproc distinto, ni de cargarlos en el orden equivocado.

from sklearn.pipeline import Pipeline
from sklearn.linear_model import LogisticRegression
import joblib

# 1. y ya representa el objetivo completo (0 = rechazado, 1 = aprobado); X ya existe

pipeline_final = Pipeline([

])

pipeline_final.fit(X, y)
